# 知識庫維護指南

## 定位

此 repository 是個人工程知識庫，不是各產品專案的規格來源。專案專屬規格應留在該專案；跨專案通用的工程方法與指南才放在這裡。

## 分類架構

- **任務／知識領域優先**：目錄代表可獨立描述的工程領域或子領域，不以工具或文件類型作為主要分類依據。
- **深度不固定**：領域可包含子領域，也可直接包含文件；不為統一層數建立空目錄。
- **按概念關係細分**：只有需要獨立知識入口時才建立子領域；工具可橫跨多個領域。
- **單一主要位置**：文件按主要回答的問題歸屬一個領域；其他領域以連結引用。
- **索引獨立**：工具、文件類型、驗證狀態與故障症狀是查詢維度，不強制成為目錄層級；可用文件 metadata 或索引維護。
- **README 必備**：每個新領域目錄都建立 README，介紹範圍、子領域、文件及交叉連結。新增或搬移文件時同一變更更新相關 README。
- **消耗式遷移**：每次遷移逐項核對來源，已完整轉移的內容在同一 PR 從舊筆記移除；未完成部分保留。舊檔清空後刪除，Git 歷史負責原始版本追溯。

## 文件類型

| 類別 | 內容 | 判斷方式 |
| --- | --- | --- |
| guides | 現行推薦做法與工作流程 | 我現在會照此執行嗎？ |
| notes | 技術概念、研究、比較與學習 | 我理解了什麼？ |
| troubleshooting | 已遇到的問題、診斷與處置 | 下次發生如何處理？ |
| examples | 可重用、可執行的最小範例 | 能否依說明重現？ |
| inbox | 尚未整理或確認的資訊 | 仍待驗證嗎？ |
| archive | 過時但值得留存的內容 | 是否不再適用？ |

## 新增與更新

1. 不確定分類時先記在 inbox，不必先設計完美目錄。
2. 優先使用 Markdown，標題具體且可搜尋；記下使用情境、環境或版本。
3. 區分已驗證事實、個人建議、尚未確認的假設；有外部依據時附來源。
4. 新結論若與舊文件衝突，更新主要入口或標示過時，不保留兩份互相矛盾的現行建議。
5. 若形成跨專案可重用的成熟做法，將文件類型由 notes 更新為 guides；不要求因此移動目錄。
6. 舊資料採**逐項消耗式遷移**：先逐條核對原文，將操作步驟、命令、範例、版本限制及不確定性保存在新位置；只移除已完整遷移的舊段落。不得僅因新文件提到同一主題就視為完成。
7. **同一 PR 同時呈現新文件與舊文件的刪改**，檢查差異、相對連結及索引；舊檔清空時刪除，未完成的部分原位保留。若原始程式範例需保留，應搬到正式範例位置或完整納入新文件，而非只連回待清理的舊目錄。
8. **遷移完成與技術驗證分開**：舊版或未驗證經驗只要連同背景、限制及不確定性完整保存，仍可完成遷移；不能把未驗證推論寫成既定事實。
9. 每個 PR 更新遷移盤點，明確標示已清除／部分剩餘／待處理，並修正 README 與引用。避免將個人路徑、公司機密、憑證或敏感資料提交到公開 repo。

## 目錄導覽與連結維護

1. 每個新建的領域目錄應有 `README.md`，說明用途並提供該目錄的文件或子目錄入口。
2. **新增、移動、重新命名或刪除文件時，應在同一個變更中更新所屬目錄的 `README.md`。** 即使只是新增單一文件也不例外。
3. 父目錄優先連結子目錄的 `README.md`，避免逐層重複列出所有文件；重要入口可例外直接連結。
4. 同一份知識只維護一個正式來源；其他主題使用交叉連結。
5. PR 審查需檢查 README 導覽、相對連結、搬移後的反向連結，以及新文件是否可由入口找到。
6. 對於尚未整理的舊目錄，可逐步補齊導覽，不必一次性搬動原始檔案。

## 文件建議格式

- **目的／適用情境**
- **內容／操作方式**
- **環境與版本**（適用時）
- **限制與待確認事項**
- **參考資料**（適用時）

不強制所有文件使用相同模板；短筆記可更簡潔。

## 維護節奏

- 新知識：隨手記錄，不強制立即整理。
- 使用舊筆記時：順手檢查是否過時並改善。
- 每月：挑選少量高價值 inbox 項目整理。
- 每季：檢查主要 guides 是否仍有效。

## AI Agent 協作

AI 可協助分類、逐項核對、檢查連結與遷移差異。依已核准的消耗式遷移流程，可在工作分支清除**確認完整轉移**的舊內容；不確定時保留並標註待處理。不得把未驗證推論寫成既定事實，正式合併前應以 PR 檢視。
