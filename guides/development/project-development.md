# 專案開發流程

> 狀態：初版整理。來源：[舊專案 SOP](../../開發/專案SOP)。這份指南提取跨專案原則，並非對所有專案強制適用。

## 建立專案

1. 明確記錄目的、預期行為、執行環境與依賴。
2. 設定版本控制，確保建置與執行步驟可重現。
3. 將環境差異放在組態中，避免寫死個人帳號、家目錄或機器路徑。
4. 規劃建置、執行、測試、日誌與故障排查的入口。
5. 視需求加入 CI、靜態分析、監控與部署流程，不必在小專案中一次導入所有工具。

## 變更流程

需求／問題 → 釐清預期行為 → 建立或更新測試 → 實作 → 驗證 → 更新文件 → 提交。

### Issue／錯誤修正的三個必答問題

每次處理缺陷 Issue，除描述症狀、重現方式、根因及修正內容外，**必須回答以下三個問題**，並記錄對應文件或工程資產是否需要調整。這個規則承襲[舊專案 SOP](../../開發/專案SOP) 的「TEST／SOP／TROUBLESHOOT」改善循環。

| 必答問題 | 對應文件／資產 | 應執行的檢查與調整 |
| --- | --- | --- |
| **為什麼之前沒發現？** | **TEST**：測試案例、測試計畫、CI 設定 | 檢查既有測試缺口；新增或修改單元、整合、系統或回歸測試，使問題在相同條件下能被發現。 |
| **怎麼避免錯誤出現？** | **SOP**：開發流程、檢查清單、部署／維護程序 | 判斷是否缺少設計審查、參數檢查、版本相容性驗證、部署檢查或操作規範；必要時更新對應流程與檢查項目。 |
| **怎麼追出錯誤源頭？** | **TROUBLESHOOT**：故障排除文件、診斷步驟、日誌與監控 | 記錄症狀、重現條件、排查過程、根因、確認方法與修復方式；若現有診斷資訊不足，評估補強日誌、錯誤訊息或監控。 |

#### 每次 Issue 的記錄格式

- **問題摘要**：症狀、影響、環境與重現條件。
- **根因與修正**：造成問題的原因、修正內容與驗證結果。
- **TEST — 為什麼之前沒發現？**：原因、需新增／修改的測試及連結；若不調整，說明理由。
- **SOP — 怎麼避免錯誤出現？**：預防措施、需更新的流程文件及連結；若不調整，說明理由。
- **TROUBLESHOOT — 怎麼追出錯誤源頭？**：診斷方法、需新增／修改的故障紀錄及連結；若不調整，說明理由。

不要求每個 Issue 都一定產生三份文件修改；**要求的是三項都經過分析，且有明確處置與可追溯的結果**。若錯誤反映預期行為定義不清，也應檢查相關規格是否需要補充或修正；不要只改測試來迎合現有實作。

測試可以先於修正建立，也可以先重現後補上；關鍵是修正完成時有可持續執行的回歸驗證。

## 運作與維護

- 長時間運作的服務應規劃日誌輪替與磁碟空間限制。
- 重要流程應能判斷目前處於哪個階段；必要時提供狀態訊息與錯誤訊息。
- 開機自啟動服務需檢查執行身分、工作目錄、環境變數及檔案權限。
- 依部署環境管理依賴，避免開發用套件意外進入正式環境。
- 重構時保留版本歷史；不要把舊專案整份複製進新專案造成搜尋與維護混亂。
