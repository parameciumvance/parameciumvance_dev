# 故障診斷工作流程

> 狀態：初版整理；來源：[舊 TROUBLESHOOT](../TROUBLESHOOT)。此處是通用診斷方法，不保證每個舊案例的根因都已確認。

## 排查順序

1. **保留現場**：記錄症狀、時間、版本、環境、重現步驟及影響。重新啟動可能恢復服務，但若允許，先保存日誌與錯誤資訊。
2. **確認執行對象**：使用 `which`、`command -v`、執行檔路徑與版本資訊，確認執行的是預期程式；檢查檔案、權限、環境變數與工作目錄。
3. **縮小範圍**：辨別編譯／連結、執行期崩潰、阻塞、網路、依賴或系統環境問題。
4. **建立假設並驗證**：一次只改動少數條件；記錄觀察、排除過的可能性及實際證據。
5. **修正與回歸驗證**：確認症狀消失且未破壞既有行為。
6. **回饋工程制度**：依[專案開發流程的 Issue 三問](../guides/development/project-development.md#issue錯誤修正的三個必答問題)檢查 TEST、SOP、TROUBLESHOOT 是否需要更新。

## 常見症狀的診斷起點

| 症狀 | 優先確認 | 注意 |
| --- | --- | --- |
| 崩潰、Segmentation fault、bad_alloc | 崩潰堆疊、記憶體存取、空指標、未定義行為、資源用量 | 舊筆記列舉的是可能原因，不能只憑症狀認定根因 |
| 程式阻塞或無回應 | 最後執行階段、等待的資料、timeout、上游連線 | 檢查逾時是否實際涵蓋阻塞操作 |
| 編譯或連結失敗 | 編譯器訊息、標頭檔與函式庫版本、連結參數 | 確認環境與實際使用的函式庫一致 |
| 網路連線失敗 | IP、路由、DNS、防火牆、目標服務是否運作 | 避免未確認原因就修改預設路由 |
| 安裝依賴後環境異常 | 套件依賴、建議安裝套件、版本來源 | 先模擬安裝或檢視依賴樹，再變更系統 |
| 重啟後無法正常恢復 | 非正常關閉、設備佔用、資源清理、啟動順序 | 納入故障恢復測試 |

## 故障紀錄格式

- **症狀與影響**
- **環境與版本**
- **重現方式**
- **排查步驟與觀察證據**
- **確認的根因**（若未知，明確標記「未確認」）
- **修正與驗證**
- **TEST／SOP／TROUBLESHOOT 後續更新**

## 原始資料保留
